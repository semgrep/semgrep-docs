This guide adds a language using tree-sitter. Grammar pins, Semgrep wrappers,
generated parsers, and language integration live in the Semgrep repository.
The upstream grammar remains in its own repository; its pinned sources are
fetched during grammar development.

## Placeholder values

The examples use `mylang` for the registry key, grammar name, and generated
parser destination. Replace it with your language's name and replace `.ext`
with its file extension (for example, `ruby` and `.rb`). Run commands from the
Semgrep repository root:

```bash
ots=libs/ocaml-tree-sitter-semgrep
```

## `semgrep` repository overview

The relevant parts of the repository are:

```text
.
├── libs/ocaml-tree-sitter-semgrep/
│   ├── core/                         # OCaml parser generator
│   └── lang/
│       ├── upstream-grammars.json    # Upstream pins and CLI versions
│       ├── ruby/                     # Generator setup and sample inputs
│       └── semgrep-grammars/src/     # Semgrep wrappers and fetched sources
├── languages/swift/
│   ├── generic/                      # CST-to-Generic-AST conversion
│   └── tree-sitter/
│       └── semgrep-swift/            # Generated C and OCaml parser
├── cli/src/semgrep/semgrep_interfaces/
│   └── generate.py                   # Language names and extensions
├── src/parsing/                      # Target and pattern parser dispatch
└── tests/
    ├── parsing/                      # Source parsing tests
    └── patterns/                     # Semgrep matching tests
```

`test-grammar` builds and tests the wrapper and OCaml parser. `regen-grammar`
copies generated files into `languages/`. Commit these files with the language
integration; no separate parser repository or publishing step is needed.

## Before adding a language

Grammar development also requires Node.js, Cargo, clang/clang++, and Git LFS on
`PATH`. Grammar targets build the generator and provision the selected
tree-sitter CLI automatically.

## 1. Register the upstream grammar

Add an entry to `$ots/lang/upstream-grammars.json`:

```json
"mylang": {
  "url": "https://github.com/OWNER/tree-sitter-mylang.git",
  "commit": "FULL_UPSTREAM_COMMIT_SHA",
  "tree_sitter": "0.26.3",
  "regen": ["mylang"]
}
```

The top-level key (`mylang`) identifies the grammar and its `semgrep-mylang`
wrapper. Each entry has these fields:

| Field         | Required | Meaning                                                                                                                                                                          |
| ------------- | -------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `url`         | Yes      | Upstream Git repository to fetch.                                                                                                                                                |
| `commit`      | Yes      | Upstream revision to check out; use a full immutable commit SHA for reproducibility.                                                                                             |
| `tree_sitter` | Yes      | Tree-sitter CLI version used to build this grammar, for example, `0.26.3`; choose one compatible with the upstream grammar.                                                      |
| `regen`       | Yes      | Generated parser destinations, for example, `["typescript", "tsx"]`; each needs its own `make regen-grammar-<dest>` command. An empty list means no Semgrep parser is generated. |
| `clone`       | No       | Local clone suffix; defaults to the key. For example, `gomod` uses `"clone": "go-mod"` to fetch into `tree-sitter-go-mod/`.                                                      |
| `depends_on`  | No       | Other registry keys whose sources must be fetched first. Defaults to an empty list.                                                                                              |

`tree_sitter` selects the CLI independently of the shared runtime version in
`$ots/core/tree-sitter-version`. Destinations in `regen` must be unique across
the registry. `clone` changes only the fetched directory name, not the wrapper
name or regeneration destinations.

Dependencies are fetched recursively at their own pinned commits before the
requested grammar. Every dependency must exist in the registry, and cycles
are invalid. For example, TypeScript declares:

```json
"depends_on": ["javascript"]
```

Fetching TypeScript therefore fetches JavaScript first. This does not
automatically test or regenerate consumers when a dependency changes: after
updating `c`, also run `make test-grammar-cpp` and `make regen-grammar-cpp`.

```bash
python3 "$ots/scripts/grammar_registry.py" validate
python3 "$ots/scripts/grammar_registry.py" fetch mylang
```

Sources are fetched into `$ots/lang/semgrep-grammars/src/tree-sitter-mylang/`.
Keep this clone gitignored.

A key can produce several destinations: `typescript` has
`"regen": ["typescript", "tsx"]`. The examples below assume one root
`grammar.js` and one destination; use the TypeScript or PHP wrappers as
references for other layouts.

## 2. Set up the wrapper and generator

Create the directories and shared build links:

```bash
mkdir -p "$ots/lang/semgrep-grammars/src/semgrep-mylang/test/corpus"
mkdir -p "$ots/lang/mylang/test/ok"
ln -s ../Makefile.common "$ots/lang/semgrep-grammars/src/semgrep-mylang/Makefile"
ln -s ../prep.common "$ots/lang/semgrep-grammars/src/semgrep-mylang/prep"
ln -s ../src/semgrep-mylang "$ots/lang/semgrep-grammars/lang/mylang"
ln -s ../Makefile.common "$ots/lang/mylang/Makefile"
```

Add representative programs to `$ots/lang/mylang/test/ok/`, for example,
`hello-world.ext`. These test the generated OCaml parser separately from the
wrapper's tree-sitter corpus.

Here is Ruby's generator setup, omitting build outputs:

```text
libs/ocaml-tree-sitter-semgrep/lang/ruby/
├── extensions.txt                    # Optional parsing statistics input
├── fyi.list                          # Sources and licenses to preserve
├── Makefile -> ../Makefile.common
├── projects.txt                      # Optional parsing statistics input
└── test/ok/
    ├── comment.rb
    ├── ex1.rb
    ├── ex2.rb
    ├── hello.rb
    ├── poly.rb
    └── rating.rb
```

### The `fyi.list` file

Create `$ots/lang/mylang/fyi.list` to list the source and license files that
explain where the generated parser came from. These are reference copies for
reviewing grammar changes, not build inputs.

Include:

- The upstream license file and grammar definition (`grammar.js` or its equivalent).
- The Semgrep wrapper's `grammar.js`.
- Additional source files used by those grammars, such as imported JavaScript modules, scanner sources, and scanner headers.
- Grammar sources and licenses from dependencies, if the grammar extends another language.

Write one file path per line, relative to `$ots/lang/`, not to the directory
containing `fyi.list`. Blank lines and full-line `#` comments are allowed;
list individual files, not directories or globs. For a simple grammar:

```text
# Upstream sources
semgrep-grammars/src/tree-sitter-mylang/LICENSE
semgrep-grammars/src/tree-sitter-mylang/grammar.js

# Semgrep extensions
semgrep-grammars/src/semgrep-mylang/grammar.js
```

For example, the first line resolves to
`$ots/lang/semgrep-grammars/src/tree-sitter-mylang/LICENSE`. Use the actual
license filename and clone directory name (including any registry `clone`
override). Every listed file must exist when regenerating.

If the upstream grammar has a scanner, also list its source, for example:

```text
semgrep-grammars/src/tree-sitter-mylang/src/scanner.c
```

Include any headers it uses and adjust the extension if it is a C++ scanner.
For dependency and dialect examples, see `$ots/lang/cpp/fyi.list` and
`$ots/lang/typescript/fyi.list`.

Do not list generated outputs such as `parser.c` or OCaml parser files.
`make regen-grammar-mylang` copies the listed files into
`languages/mylang/tree-sitter/semgrep-mylang/fyi/`, preserving their relative
paths, and writes Git provenance to `fyi/versions` automatically.

## 3. Extend the grammar with Semgrep syntax

Create `$ots/lang/semgrep-grammars/src/semgrep-mylang/grammar.js`:

```javascript
const base = require("tree-sitter-mylang/grammar");

module.exports = grammar(base, {
  name: "mylang",
  rules: {},
});
```

This initially inherits the upstream grammar unchanged. Extend its rules to
accept metavariables and ellipses. For a grammar with an `expression` rule,
an ellipsis alternative can look like:

```javascript
expression: ($, previous) => choice(previous, $.ellipsis),
ellipsis: $ => '...',
```

Add input and expected syntax trees under the wrapper's `test/corpus/`.
Use `$ots/lang/semgrep-grammars/src/semgrep-fga/` as a small example.
The shared `prep` script imports the upstream scanner and corpus; use a custom
script for additional headers or a different upstream layout.

## 4. Test and generate the parser

```bash
make test-grammar-mylang
mkdir -p languages/mylang/tree-sitter/semgrep-mylang/
make regen-grammar-mylang
```

Regeneration requires the destination directory to exist. It writes this layout:

```text
languages/mylang/tree-sitter/semgrep-mylang/
├── lib/                              # C and OCaml parser, CST, boilerplate
├── bin/                              # Standalone parser entry point
├── config/                           # Build configuration
└── fyi/                              # Source provenance and licenses
```

Register the C parser with Git LFS before staging it:

```bash
git lfs track 'languages/mylang/tree-sitter/semgrep-mylang/lib/parser.c'
```

Change the wrapper and regenerate instead of editing generated files by hand.

See [updating a grammar](/contributing/updating-a-grammar) for CST checks and
updates to dependent grammars.

## 5. Integrate the parser in Semgrep

Now that you have generated the parser for `mylang`, connect it to Semgrep.
Use `languages/fga/` as an integration example.

<Steps>
  <Step>
    Add the language name and file extensions to
    `cli/src/semgrep/semgrep_interfaces/generate.py`, then regenerate the interfaces:

    ```bash
    make -C cli/src/semgrep/semgrep_interfaces
    ```

  </Step>
  <Step>
    In `src/parsing/Check_pattern.ml`, add the language to
    `lang_has_no_dollar_ids`. Return `true` if dollar identifiers are invalid
    in the language, or `false` otherwise.
  </Step>
  <Step>
    In `src/printing/Pretty_print_AST.ml`, add the language to the appropriate functions:

- print_bool
- if_stmt
- while_stmt
- do_while
- for_stmt
- def_stmt
- return
- break
- continue
- literal

          </Step>
        <Step>

  Create `languages/mylang/generic/Parse_mylang_tree_sitter.ml` using the
  generated `languages/mylang/tree-sitter/semgrep-mylang/lib/Boilerplate.ml`
  as a starting point. Add a corresponding `.mli`.

            `Boilerplate.ml` provides `map_*` functions that traverse the CST and
            construct `Tree_sitter_run.Raw_tree` values. Adapt them to construct
            `AST_generic` nodes instead.

            Follow `languages/fga/generic/Parse_fga_tree_sitter.ml` to define `parse`
            and `parse_pattern`, using `Parse_tree_sitter_helpers` for parser wrapping
            and token locations. Keep this hand-written converter separate from
            `Boilerplate.ml`, which regeneration overwrites.

            This file should contain something similar to:
            ```ocaml
            module H = Parse_tree_sitter_helpers

            let parse file =
            H.wrap_parser
            (fun () ->
            Parallel.backtrace_when_exn := false
            Parallel.invoke Tree_sitter_X.Parse.file file ()
            )
            ```

          </Step>

        <Step>

  Add the OCaml library definitions, using
  `languages/fga/generic/dune` as an example, and link the converter from
  `src/parsing/dune`. The generated parser already lives under
  `languages/mylang/tree-sitter/semgrep-mylang/`; no submodule is needed.

      </Step>

  <Step>
  Route target and pattern parsing to the converter in
  `src/parsing/Parse_target.ml` and `src/parsing/Parse_pattern.ml`.
</Step>
<Step>
  Add a case to `dump_tree_sitter_cst` in
  `src/parsing/tests/Test_parsing.ml`, following Ruby's use of
  `Tree_sitter_ruby.Parse.file` and `Tree_sitter_ruby.Boilerplate.dump_tree`.
  Add `tests/parsing/mylang/hello-world.ext`, then build and inspect its CST:

            ```bash
            make core
            bin/semgrep-core -lang mylang -dump_tree_sitter_cst tests/parsing/mylang/hello-world.ext
            ```

          </Step>

      </Steps>

Implement the translator from the tree-sitter CST into Semgrep's Generic AST
for both target code and patterns, including metavariables and ellipses.
You can translate directly, as FGA does, or first translate into a
language-specific AST and then into Generic AST. The generated boilerplate
supplies the traversal structure; you must implement the language semantics.

## 6. Add parsing and rule matching tests

Add source files under `tests/parsing/mylang/` to exercise supported syntax,
starting with `hello-world.ext`. For example, see
`tests/parsing/fga/hello-world.fga`.

Add matching tests under `tests/patterns/mylang/`. Each test pairs a source
file such as `dots_args.ext` with a pattern file named `dots_args.sgrep`.
Mark expected matches in the source with `ERROR:` comments, using the
language's comment syntax. See `tests/patterns/fga/dots_args.fga` and
`tests/patterns/fga/dots_args.sgrep` for an example.

Cover literal patterns, metavariables, and ellipses, including code that should
not match. These tests check Semgrep's CST-to-AST conversion and matching,
beyond the wrapper corpus and standalone parser tests.

```bash
make core
make test
```

## Parsing statistics

`projects.txt` and `extensions.txt` are optional inputs for parsing benchmarks.
For example, after building Ruby's grammar:

```bash
make test-grammar-ruby
make -C "$ots/lang/ruby" stat
```

The `stat` target downloads projects from `projects.txt` and reports parsing
success for file extensions listed in `extensions.txt`.

## Troubleshooting

- C/C++ compilation errors: check that `prep` imports the scanner and required headers.
- Missing JavaScript modules: check `require()` paths and registry `depends_on` entries.
- Syntax errors: inspect the corpus output for `ERROR` nodes and reduce the failing input.
- OCaml generation or reparsing errors: preserve a minimal reproducer and investigate the generator.

Report upstream grammar bugs with minimal examples.

## Legal concerns

Be thankful for the authors of the original code, keep clearly visible
license notices, and make it easy to get back to the original projects:

- Make sure to preserve the `LICENSE` files. List them in
  `$ots/lang/mylang/fyi.list`.
- For sample input in `test/`, consider Public Domain ("The
  Unlicense") files or write your own, for simplicity.
  [GitHub Search](https://github.com/search/advanced)
  allows you to filter projects by license and by programming language.
